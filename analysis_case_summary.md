# Banking Customer Segmentation & Transaction Analytics — Case Summary

## 1. Business Context

This case study simulates a retail banking environment in which an analytics team needs to understand customer value, engagement, product depth, transaction behavior, and geographic distribution.

The dataset is simulated and should be treated as a demonstration dataset rather than evidence about actual banking customers or markets.

## 2. Analytical Questions

The analysis focuses on:

- Which customers generate the highest credit inflows and debit activity?
- Which customers are active, low-activity, or dormant?
- Which customers have single-product versus multi-product relationships?
- Which transaction services are most frequently used?
- How do customer value and engagement vary across cities?

## 3. Data Model

### Customers

Contains:

- Customer ID
- Name
- Gender
- Date of birth
- Signup date
- City

### Accounts

Contains:

- Account ID
- Customer ID
- Account number
- Account type
- Open date
- Balance

Account types generated by the current simulation are:

- Savings
- Current
- Loan

### Transactions

Contains:

- Transaction ID
- Account ID
- Transaction date
- Amount
- Transaction type
- Description

The simulation generates 200 customers and 2,000 transactions, with customers receiving 1–3 accounts.

## 4. Analytical Workflow

```
Data Generation
      ↓
Data Quality Validation
      ↓
Customer Feature Engineering
      ↓
Segmentation
      ↓
Business Analysis
```

## 5. Data Quality

The validation layer checks:

- Record counts
- Null customer/account/transaction keys
- Orphaned account records
- Orphaned transaction records
- Duplicate account numbers
- Invalid transaction types
- Non-positive transaction amounts
- Future transaction dates
- Negative account balances

These checks establish whether the relational data is suitable for downstream customer analysis.

## 6. Customer Feature Engineering

The feature layer creates one row per customer.

### Core Features

- `account_count`
- `product_count`
- `relationship_balance`
- `total_credit`
- `total_debit`
- `transaction_count`
- `avg_transaction_value`
- `active_months`
- `last_transaction_date`
- `credit_debit_ratio`
- `salary_transaction_count`
- `salary_credit_amount`

The feature layer deliberately separates reusable customer-level metrics from downstream segmentation rules.

## 7. Segmentation Framework

### Customer Value

Customers are ranked using total credit inflows and divided into three data-driven tiers using `NTILE(3)`:

- High Value
- Medium Value
- Low Value

This avoids imposing arbitrary monetary thresholds on a randomly generated dataset.

### Engagement

Engagement is based on transaction recency:

- **Active:** transaction within 90 days
- **Low Activity:** 91–365 days
- **Dormant:** no transaction or more than 365 days since last transaction

### Product Relationship

Product depth is based on distinct account types:

- **Single Product:** one product type
- **Multi Product:** more than one product type

## 8. Combined Customer Profiles

The three dimensions can be combined to identify analytically useful profiles, for example:

| Value | Engagement | Product Depth |
|---|---|---|
| High | Active | Multi |
| High | Dormant | Multi |
| Medium | Active | Single |
| Low | Active | Single |

These are descriptive customer profiles, not predictive scores.

## 10. Business Implications

The resulting segments can support questions such as:

- Which high-value customers are also active and multi-product?
- Which valuable customers have become dormant?
- Where are single-product relationships concentrated?
- Which cities have high customer activity but lower product depth?
- Which transaction services dominate usage?

These questions can inform further analysis around relationship management, reactivation, product adoption, and regional service planning.

The project does not claim that these actions will produce a specific commercial outcome because the dataset is simulated and lacks real-world profitability, campaign, cost, and outcome data.

## 12. Analytical Boundary

This project should be presented as a **SQL customer analytics case study**, not as a real-world banking performance analysis.

It does not measure:

- Actual bank profitability
- Customer lifetime value
- Default or delinquency risk
- Real customer satisfaction
- Causal drivers of banking behavior
- Actual regional market share

The strongest portfolio signal is the workflow:

> **Raw Data → Quality Checks → Customer Features → Segmentation → Business Analysis**
